How agents talk to each other — unprompted

AutoGen vs AG2, the A2A/MCP protocol layer, and a path to wiring your own Claude + Gemini agent mesh that can phone home for context & credentials.
Prepared for Gyasi Sutton Date 2026-05-28 Method 2× Gemini deep-research + multi-hop web synthesis Status Discussion draft — for review & paired-debate

You asked a precise question: how can different agents (coding agents, harnesses) talk to each other without being prompted each time — including the case where a sub-agent you handed a task realizes it's missing something and comes back to ask for more background or the credentials to connect to an app. This report answers that, and lays out the direction you're leaning toward.

The path you're leaning toward

An A2A-style JSON message mesh, with two transport tiers and a credential gate:

  • Tier 1 — async "mail" JSON messages dropped in a shared bus/file inbox; an agent is alerted when its name is called. Like email between agents — durable, survives restarts.
  • Tier 2 — realtime "in the room" a swarm/event-bus layer for quick, low-latency back-and-forth when agents are live together.
  • Credential gate — CIBA when an agent needs secrets, it doesn't get the raw .env — it triggers an out-of-band approval and receives a short-lived scoped token.

That instinct is well-aligned with where the industry landed in 2025–2026. Below is the full picture so you can decide the next steps machine-to-machine — this is a map of the path, not an argument to eliminate options.

01The AutoGen / AG2 split (why it's confusing)

Your "autogen now ag2 i think" is correct — and the confusion is real, not yours. In November 2024 the original creators (incl. Chi Wang) left Microsoft and forked the project. There are now two things, and they handle "unprompted" in opposite ways.

Gotcha

The old PyPI names (autogen, pyautogen) now install AG2, the fork — not Microsoft's rewrite. Microsoft's new framework only lives under the autogen-core / autogen-agentchat namespaces. Installing the wrong one is the #1 source of broken tutorials.

02The 3 ways agents talk (the whole field reduces to these)

Every framework, every protocol, is one of these three under the hood:

1 · Direct call (RPC)

A explicitly calls B and waits. prompted synchronous AG2 initiate_chat, OpenAI handoffs. Simple, but blocks — and a sub-agent that needs to pause will time out.

2 · Moderated turn-taking

A manager picks who speaks next. semi-autonomous AG2 GroupChatManager, AutoGen SelectorGroupChat. The agent doesn't choose to speak — the manager does.

3 · Publish / subscribe (event bus) — this is "unprompted"

A publishes a message to a topic; any agent subscribed receives it, with no orchestrator deciding the turn. An agent emits an event and others react. truly agent-initiated async This is exactly what you described — "an agent can send and talk to other agents unprompted."

03Microsoft AutoGen 0.4 — the genuine unprompted mechanism

This is the actor model. An agent is a RoutedAgent, decorates handlers with @message_handler, and publish_message() to a topic. Anyone subscribed reacts — nobody told it to.

from dataclasses import dataclass
from autogen_core import RoutedAgent, message_handler, TopicId, default_subscription

@dataclass
class AnomalyDetectedEvent:
    description: str
    severity: int

class MonitorAgent(RoutedAgent):                 # PUBLISHER
    async def run_continuous_scan(self):
        if self.found_anomaly():
            # UNPROMPTED: the agent itself decides to broadcast
            await self.publish_message(
                AnomalyDetectedEvent("CPU spiking", severity=9),
                topic_id=TopicId(type="alerts", source="server_1"),
            )

@default_subscription                            # SUBSCRIBER
class ResponderAgent(RoutedAgent):
    @message_handler
    async def handle_anomaly(self, message: AnomalyDetectedEvent, ctx) -> None:
        # Wakes up unprompted when a message hits the subscribed topic
        if message.severity > 8:
            print("CRITICAL — initiating mitigation")

Key behaviors that matter for your design:

  • Publish is one-way / fire-and-forget — no return value. If you need an answer, the other agent publishes its own message back. This is precisely how phone-home works: the sub-agent just publishes a NeedMoreContext event whenever it wants.
  • An agent won't receive its own published message (built-in loop prevention).
  • It also supports direct request/response (send_message) when you do want a blocking answer.
  • The runtime natively persists actor state & event logs → durable, long-running agents that survive restarts.

On top of the core, the autogen-agentchat layer rebuilds familiar team constructs: RoundRobinGroupChat, SelectorGroupChat (LLM picks next speaker), Swarm (handoffs), Magentic-One (Orchestrator + Task/Progress Ledgers + WebSurfer/FileSurfer/Coder workers), and GraphFlow (deterministic DiGraph state machines with message filtering).

04AG2 (the fork) — Swarm + handoffs = semi-autonomous

AG2 keeps the conversational model but adds Swarm, where agents hand off control to each other autonomously based on conditions — no human re-prompting each step.

from autogen.agentchat.contrib.swarm_agent import (
    AfterWorkOption, OnCondition, register_hand_off
)

register_hand_off(agent=triage_agent, hand_to=[
    OnCondition(flight_agent,  "User wants to cancel or modify a flight."),
    OnCondition(billing_agent, "User has a billing question."),
])

register_hand_off(agent=flight_agent, hand_to=[
    OnCondition(billing_agent, "Flight cancelled. Proceed to refund."),
    ],
    after_work=AfterWorkOption.REVERT_TO_USER,   # stuck? phone home to the human
)
  • OnCondition → becomes a function the LLM can call; the agent itself decides "I should hand this to billing now." Agent choosing to talk to another agent, unprompted by you.
  • OnContextCondition → handoff fires automatically from shared-memory state changes.
  • AfterWorkOption → the fallback when no tool is called: TERMINATE, STAY, or REVERT_TO_USER (your escape hatch to a human).

For free-for-all chat: GroupChat + GroupChatManager with speaker_selection_method = auto (LLM picks), round_robin, random, manual, or a custom Python function. Human-in-the-loop is via UserProxyAgent with human_input_mode = ALWAYS / TERMINATE / NEVER.

Why Swarm handoffs beat LLM speaker-selection

SelectorGroupChat burns an extra LLM call between every turn and can hallucinate the next speaker or loop. Swarm handoffs are plain tool-calls — and models are heavily fine-tuned for accurate JSON tool-calling, so routing is more reliable and cheaper.

05The protocol layer — A2A vs MCP (don't conflate them)

This is central to the path you're choosing. The two protocols are complementary, not competing:

MCP — agent ↔ tools

Anthropic's Model Context Protocol. Gives one agent a USB-port to databases/APIs. The agent sees inside the tool (typed function signatures). JSON-RPC 2.0 over stdio (local) or SSE/HTTP (remote). Vertical integration.

A2A — agent ↔ agent

Google's Agent2Agent (donated to the Linux Foundation, June 2025). Agents stay opaque to each other; B publishes an "Agent Card" (JSON at a well-known URL describing skills + auth) and others discover & task it. Horizontal collaboration.

The A2A task lifecycle is submitted → working → input-required → completed. That input-required state is the standardized "agent phones home for more info" you're describing — baked into the protocol. IBM's ACP merged into A2A v1.0 (Aug 2025), adding enterprise state-sync & fault tolerance. Cisco's AGNTCY ("Internet of Agents") provides the registry + transport (DNS/TCP-IP for agents). ANP is the decentralized/Web3 variant using W3C DIDs.

 MCPA2A (+ACP)AGNTCYANP
FocusAgent→tools/dataAgent↔agentAgent network fabricDecentralized agentic web
DiscoveryExplicit configAgent Cards (JSON)OASF + directoryW3C DID / WNS
TransportJSON-RPC (stdio/SSE)JSON-RPC over HTTPS/SSE + webhooksSLIM, gRPC, HTTP/2P2P network

Most production stacks run both: MCP for each agent's tools, A2A for agent-to-agent. For mixing Claude + Gemini specifically across machines, A2A is the vendor-neutral bridge.

06Your scenario: the "phone-home for context / credentials" loop

Your story: Claude gives a sub-agent a task. Ideally Claude front-loads everything, but the sub-agent might realize mid-task it needs more background, or the env/creds to connect to an app — and should be able to come back and ask, unprompted. This is a named pattern with two halves.

(a) The pause-and-ask — durable interrupt

The cleanest model is LangGraph's interrupt(): a node pauses, checkpoints its full state to a DB, and waits. The parent (or you) supplies the missing info, and it resumes from exactly where it stopped.

from langgraph.types import interrupt, Command

def sub_agent_node(state: dict):
    if not state.get("db_credentials"):
        # Agent initiates a phone-home for missing context
        creds = interrupt({"reason": "need_db_credentials", "agent": "sub_agent_1"})
        state["db_credentials"] = creds       # resumes here once provided
    return do_work(state)

# Resume from the orchestrator OR a human/Slack channel:
# graph.invoke(Command(resume={"user":"admin","pass":"..."}),
#              config={"configurable": {"thread_id": "123"}})

Equivalents in other frameworks:

  • AG2: AfterWorkOption.REVERT_TO_USER or a UserProxyAgent.
  • AutoGen 0.4: the sub-agent publishes a NeedInput event; an orchestrator/UserProxy subscribed to that topic answers.
  • OpenAI Agents SDK: a handoff() back to the orchestrator or a Human agent; on_handoff middleware can inject JIT credentials during the transition.
  • Semantic Kernel: HandoffOrchestration — a mesh topology that natively pauses for human input when no peer can satisfy the need.
  • Google ADK: RemoteA2aAgent streams an event back over A2A JSON-RPC; orchestrator intercepts it without breaking the session.

(b) Handing over secrets safely (do NOT paste .env into a prompt)

The principle

Front-load non-secret context. For secrets, the sub-agent requests just-in-time, scoped tokens via an approval channel — never the raw long-lived key. If a hijacked agent (via prompt injection) holds a static key, it can exfiltrate it with one outbound request.

  • CIBA (Client-Initiated Backchannel Authentication): the agent says "I need to connect to X," an out-of-band channel (Slack/phone) asks the human to approve, and on approval the agent gets a scoped, short-lived token.
  • JIT secret brokers (e.g. Aembit): the agent never holds the secret; a broker checks intent + policy + the agent's workload identity (SPIFFE / W3C DID) and mints a ~60-second ephemeral token for that one task.
  • ESCALATE.md: a lightweight convention — agent posts a request, human replies APPROVE/DENY in Slack/email, all logged.

08Messaging channels AS the transport (Slack / email)

Your "Slack messages or emails like features" is a real, common transport. An agent DMs you (or another agent) and waits for the reply as its input:

  • Webhook-wrapper pattern: agent calls a request_human_input tool → HTTP POST to a Slack webhook → execution suspends (persistent checkpointer) → human replies / clicks Approve → backend locates the paused thread_id and resumes the graph.
  • Slack's 3-second rule → apps 200 OK immediately, process async in the background.
  • Mutation tools return a confirmation card; the real write only happens on Approve. Tools like polos / hitl-agent-ts wrap this over LangGraph interrupts.

09Security — the part most people skip

The "lethal trifecta"

Danger = private-data access + exposure to untrusted content + external communication. An agent-initiated comms mesh has all three by design, so contain it deliberately.

  • Prompt injection → exfiltration: a poisoned README/issue can tell an agent to send its keys out. Static env-var secrets make this trivial — hence JIT tokens (§6b).
  • Sandbox execution: run agents in Docker with no internet egress (IPAddressDeny=any) except allow-listed domains.
  • Kernel-level guards: eBPF tools (e.g. Inner Warden) block a hijacked agent's unauthorized syscalls / anomalous "phone-home" IPs at wire speed.
  • Verifiable identity: A2A v1.0 signed Agent Cards; SPIFFE / W3C DID workload identity so the broker knows which agent is asking before minting a token.

10The recommended path for your setup

Putting your instinct together with the research, here's a concrete shape — a two-tier JSON mesh + a credential gate, vendor-neutral so Claude and Gemini both plug in:

┌─────────────────────────────────────────────────────────────┐ │ ORCHESTRATOR (Claude) │ │ delegates tasks · front-loads non-secret context │ └───────────────┬───────────────────────────┬─────────────────┘ │ │ Tier 2: REALTIME "in the room" Tier 1: ASYNC "mail" (event bus / channels / tmux) (JSON inbox: SQLite or files) │ │ ┌─────────▼─────────┐ ┌─────────▼──────────┐ │ sub-agent (Claude)│ │ sub-agent (Gemini) │ │ publishes: │ │ drops message: │ │ NeedContext ●────┼───────▶│ "need DB creds" │ └─────────┬─────────┘ └─────────┬──────────┘ │ │ ▼ needs a SECRET? ▼ ┌───────────────────── CIBA / JIT broker ──────────────────┐ │ out-of-band approval (Slack DM) → scoped 60s token │ │ never the raw .env │ └──────────────────────────────────────────────────────────┘

Why this shape

  • Two tiers because the two needs are genuinely different. "Mail" (durable JSON inbox) is right for delegated work that may sit for minutes/hours and must survive a restart. "In the room" (event bus / Claude channels) is right for quick live back-and-forth. You named this distinction yourself — it's correct.
  • JSON messages + name-addressing = the A2A mental model without forcing full A2A on day one. You can start with a SQLite taskbox / JSON inbox and graduate to formal A2A Agent Cards when you need cross-machine or cross-vendor discovery.
  • CIBA as the credential gate keeps the scary part (secrets) out of prompts and behind an approval you see.
  • Vendor-neutral so a Gemini result and a Claude session are just two nodes on the same bus.
Build order (cheapest first, matches your local-first instinct)
  1. Start with Tier-1 mail: a shared SQLite "taskbox" (or JSON-file inbox) + a tiny MCP server that lets any agent send(to, msg) / inbox(). Proves the loop with zero heavy infra.
  2. Add the phone-home: give sub-agents a request_more(reason) tool that writes a NeedContext row; orchestrator polls/subscribes and answers. (LangGraph interrupt() if you want durable pause/resume.)
  3. Add Tier-2 realtime only where latency hurts: Claude Code Agent Teams / channels for live sessions, or AutoGen 0.4 pub/sub if you want a real event bus.
  4. Add the CIBA credential gate before any agent touches a real secret.
  5. Graduate to A2A Agent Cards when you need Claude↔Gemini across machines or want formal discovery.
